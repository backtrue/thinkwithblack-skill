## MK-164 v0.5｜Portray a Persona Using Reference Lists (2026-10-02)

This is the approved method update, not a verbatim quotation from the original course. The workflow below addresses the need to portray a Persona with a set of interest labels, replacing selection based only on product categories. Retain the original course's audience-size advice as historical context; this version does not control audience size

### Purpose and Scope
Deliver a set of candidate interest labels that together portray the Persona's everyday life. Start with the Eachspy 2026-09-23 and Primenumbers 2026-10 reference lists. This version does not call APIs, inspect the Meta interface, require official IDs, configure OR/AND, age, exclusions, or budgets, or create audiences or ads. Leave live platform availability and performance unknown; missing accounts, IDs, or connections do not block this version's work

### Inputs and Data
Read the user-specified Persona and authorized background first; do not ask again for existing information. Distinguish source statements, Persona hypotheses, and unknowns. Do not invent occupation, income, brand preferences, or current purchase intent
See the reference lists in the same directory: [Appendix: interest-reference.md](#reference-2), [Appendix: eachspy-302-interests.csv](#reference-1), and [Appendix: primenumbers-interests.csv](#reference-3). Preserve original names, categories, sources, and snapshot dates; place Chinese translations in a separate field without presenting them as official platform names. These references are not a complete or live inventory of targetable labels

### Workflow
1. Describe the person in one paragraph, organizing their life priorities, preferences, daily activities, content interests, brands, and values; use only known dimensions
2. Actually read the lists and select candidates across categories. For each, explain “which Persona trait → which dimension the label portrays → why it belongs in the set.” Product-category relevance alone is insufficient; label inferred connections as hypotheses
3. Review candidates together for a consistent portrayal; remove duplicates, contradictions, overly broad items, and items without supporting clues. Do not set a fixed label count or equate quantity with precision
4. Deliver a description of the overall portrayal and a row-by-row table: Persona trait, original candidate name, Chinese translation for readability, portrayed dimension, reason for inclusion, fact/hypothesis, source and snapshot date, and verification status
5. List traits the reference lists cannot portray; do not force unrelated labels into the gaps

### Missing Inputs and Acceptance
If the specified Persona cannot be found, stop dependent label selection and ask for its source; if only some dimensions are missing, first deliver the supported portion. Retain gaps when the lists lack a matching label; this version does not automatically switch to an API. Every candidate must trace back to the Persona and a reference list, and the whole set must explain the person it portrays. Consistently label the result “Candidate labels organized from reference lists; current Meta availability has not been confirmed”
