# MK-436｜網站漏斗事件規劃

一般對話請上傳 `packs/mk-436.md`，其中已包含共用規則、本文及必要參考

## 工作目的

這個技能交付：**節點、行動、事件與價值定義**

跨平台曝光相加不是去重觸及；不同歸因窗的轉換不能直接當全站真實訂單相加

## 必要資料

請提供：網站或 App 的實際流程、商業目標、要觀察的動作與頁面、可用訂單或事件識別鍵、既有追蹤設定；未建置時提供預定流程

## 方法步驟

1. 先畫出從來源／媒介到站內行為、目標與價值的流程，再決定哪些節點需要事件追蹤
2. 核心要回答：使用者從哪裡來、觸發什麼事件、完成什麼目標、創造多少價值
3. 事件不一定全部由 GA 記錄，也可以是活動或其他可驗證行為；沒有商業決策用途的事件不為追蹤而追蹤

## 計算與判讀

核對資料來源、日期、幣別、分母與歸因；跨平台相加不等於不重複觸及或增量

## MK-436 補充方法：先定義同一批漏斗單位，再計算完成率

規劃商品瀏覽、加購、開始結帳、付款時，每個節點先列觸發行動、資料來源、統計單位、關聯 ID、去重方式、期間與付款狀態。事件觸發次數、去重工作階段、去重結帳及付款訂單張數是不同單位；重新整理或重複送出事件不代表新增一位顧客或一筆結帳

計算完成率前，先證明分子與分母使用相同單位、同一批對象與相容的觀察期間，而且完成付款的單位是該批開始結帳單位的子集。例如按 checkout ID 去重，先固定該批開始結帳 ID，再核對其中哪些 ID 在指定觀察窗口內確實付款；分子與分母均計去重 checkout ID。若採工作階段或顧客，也必須先確認一致的關聯與去重定義，不能把付款訂單張數直接代入

結帳完成率或漏斗轉換率要使用開始結帳事件數及付款訂單數前，必須先確認兩者的去重單位、對象期間與付款歸屬相容。尚未核對時，明寫「目前無法計算結帳完成率」；不得用這兩類數字計算或呈現完成率／轉換率，也不得以警告、反例、引述或比較方式寫出這種混算率。改用純文字說明口徑缺口。這項限制不禁止分開列出原始數字、各自同口徑的變化，或依訂單與事件核對方法報告可驗證的彙總差異；不能據此斷言結帳完成率下降或某欄位造成流失

假設示例也遵守相同停點。若要示範完成率，必須先明示分母為同一批去重結帳 ID，分子為其中在指定窗口內已付款的去重結帳 ID。若只有不同統計單位的計數，只保留符合相同口徑的示例及待補證據，不展示或計算混合計數的比率

缺資料仍先完成節點、行動、事件與價值定義表，列出事件與訂單如何用關聯 ID 核對、重複事件如何處理、付款／退款狀態與跨週完成如何歸屬，以及每週要查的差異。追蹤規劃不代表事件已安裝、成功觸發或資料已核實，也不預先判定實際流失原因

漏斗比較使用同單位、同期間與付款子集口徑
